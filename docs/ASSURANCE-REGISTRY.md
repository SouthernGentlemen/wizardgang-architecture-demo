# Assurance registry contract

`assurance/registry.json` is the single authoritative inventory for canonical assurance structured data. A canonical assurance JSON file is not accepted merely because it exists under `assurance/`; it must be registered with a stable dataset identity, resource family, role, declared JSON Schema, public/private classification, and capabilities.

The seven released logical public families remain the primary API datasets. A family may declare additional `resources` when it owns more than one structured dataset or partition. The compliance family therefore registers ISO/IEC 27001, ISO/IEC 42001, the WCAG 2.2 manifest, and all four WCAG principle partitions without introducing a second registry. The non-route `governance.records` family similarly registers 14 reportable-table partitions without making generated Markdown or a giant aggregate blob authoritative. Lifecycle metadata and operational monitoring are registered by the same file as control-plane and operations resources.

Node-side assurance tooling must discover controlled paths through `scripts/lib/assurance-registry.mjs`. The registry completeness validator rejects duplicate identities, duplicate registered paths, missing files or schemas, and any canonical `assurance/**/*.json` file that is not registered. It validates every registered document against the exact schema named by its registry entry and reports both the dataset path and failing schema location.

All record-aware semantic validation and deterministic presentation must use the shared registry-discovered record inventory, not the primary `api-index` file as a substitute for a resource family. Evidence and relationship targets therefore resolve across every registered partition, and evidence/risk domain rules apply to records wherever the registry places them. Framework-specific ISO and WCAG validators keep their normative coverage rules, but obtain the canonical data path, schema path, framework metadata, and record collections from the registry so supported relocation does not create a second path inventory.

Worker code cannot dynamically import arbitrary JSON paths, so `scripts/generate-assurance-runtime-binding.mjs` deterministically generates `src/assurance/generated/registry-bindings.ts` from resources declaring the `runtime` capability. CI checks the generated bytes. Runtime code imports only that generated binding rather than maintaining another list of assurance files.

Release snapshots use the registry-declared dataset paths plus `assurance/registry.json` as their digest corpus. SoA summary generation discovers resources with the `summary-source` capability and projects the complete registered record family for that source/framework. Lifecycle, integrity, and operational validation likewise resolve datasets through the shared registry layer. This keeps file discovery centralized while preserving framework-specific semantic validation, disclosure review, evidence freshness, relationship checks, and stable record IDs.

Governance register generation discovers every `governance-records` resource with `summary-source`, validates the common schema, and replaces only the content between each deterministic `GENERATED:governance-records` marker pair. Those resources intentionally do not declare `runtime` or public API routes: they own reportable governance table state without adding a Worker data copy. Policy prose and other non-reportable tables remain outside those markers.

Use `npm run generate:assurance-runtime-binding` after changing runtime-capable registry entries. Run `npm run validate:assurance` to enforce registry completeness, JSON Schema validation, binding agreement, lifecycle and integrity semantics, deterministic summaries, and operational monitoring controls.

## Route ownership and matching

Assurance route ownership is derived from the same registry declarations used by Worker dispatch and route-manifest generation. `src/routing/assurance-routes.ts` compiles those owners into the common declarative route system; `src/router.ts` delegates to that module and contains no assurance family/path dispatch table. The JSON registry remains authoritative for canonical HTML, collection API, and exact-record API paths.

Current specialized renderers and focused API adapters register by stable registry owner ID under `src/assurance/route-capabilities/`. Those capability modules do not own URL strings. A registered dataset API with valid `runtime`, `records`, and `api-index` capabilities can use the shared `genericAssuranceResponse` without a family-specific router entry, while a registered HTML presentation must explicitly supply its specialized renderer. Missing or contradictory handler capabilities fail router construction.

Matching does not depend on declaration order. The common declarative matcher checks exact paths before parameter routes, so a declared nested collection such as `/v1/assurance/compliance/risks` owns that literal path even when `/v1/assurance/compliance/{id}` also exists. Exact static paths must still be globally unique. Intersecting detail templates are rejected rather than resolved by order.

An `apiRecord` placeholder must be exactly one complete path segment. Route selection splits the raw pathname before parameter decoding, so an encoded slash remains within one identifier segment rather than creating a second route segment. The declarative matcher normalizes the decoded parameter, and the assurance adapter re-encodes it before passing it to the existing exact-record handler so the current single-decode record lookup contract is preserved. Extra path segments are not absorbed into the identifier.

Route owners must declare the registry capabilities needed by their routes: runtime-backed routes require `runtime`, collection APIs require `api-index` and `records`, and exact-record APIs require `records`. The active assurance router additionally rejects aliases, specialized handlers without a corresponding registry route, and HTML routes without a registered renderer. `scripts/generate-route-manifest.mjs` consumes the same route declarations and dataset routes when generating or checking `docs/route-manifest.json`; `validate:assurance` enforces the shared route contract before the generated artifact is accepted.

Focused APIs remain thin adapters over the shared query handler. Disclosure projection, filtering, pagination, exact record lookup, response envelopes, CORS, ETags, and cache headers therefore remain in the current assurance HTTP contract rather than being duplicated in route dispatch. The advisory `/security` offline exception is represented by local route capability metadata instead of a central path exception. No assurance aliases or legacy media/schema negotiation are introduced.

## Published DEMO-125 history exception

The published main-branch commit `207fd4e146054bd3c9da236c615753df9f927610` has the valid controlled title `[DEMO-125] [OPS] Canonicalize assurance data and release snapshots`, but its commit body predates this correction and omits the required `Change:`, `Reason:`, `Risk:`, `Validation:`, `Source:`, and `Release:` sections. Rewriting that published commit would alter shared history, so DEMO-126 does not rewrite it.

`scripts/validate-history.mjs` contains one SHA-exact exception for that immutable commit body only. The exception does not accept a different SHA, does not relax controlled-title or sequential DEMO-ID validation, and does not weaken body validation for DEMO-126 or any future controlled change. CI continues to run `validate:history` as a required failing gate; it is not marked `continue-on-error`.
