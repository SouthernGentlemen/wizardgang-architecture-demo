# Assurance registry contract

`assurance/registry.json` is the single authoritative inventory for canonical assurance structured data. A canonical assurance JSON file is accepted only when registered with a stable dataset identity, resource family, role, declared JSON Schema, public/private classification, and capabilities.

Logical families may declare additional resources when they own multiple structured datasets or partitions. Compliance registers ISO/IEC 27001, ISO/IEC 42001, the WCAG 2.2 manifest, and its principle partitions without introducing another registry. The non-route `governance.records` family similarly registers reportable-table partitions without making generated Markdown authoritative. Lifecycle metadata and operational monitoring are registered as control-plane/operations resources.

Node-side tooling discovers controlled paths through `scripts/lib/assurance-registry.mjs`. Completeness validation rejects duplicate identities/paths, missing files or schemas, unregistered canonical assurance JSON, and schema failures. Record-aware semantic validation and deterministic presentation use the same registry-discovered inventory so evidence and relationship targets resolve across registered partitions.

Worker code cannot dynamically import arbitrary JSON paths, so `scripts/generate-assurance-runtime-binding.mjs` deterministically generates `src/assurance/generated/registry-bindings.ts` from resources declaring the `runtime` capability. CI checks the generated bytes. Release snapshots use registry-declared dataset paths plus `assurance/registry.json` as their digest corpus.

SoA and governance-register generation discover registered `summary-source` resources and project canonical structured state into Markdown. Generated Markdown is presentation evidence, never a second editable assurance-state authority.

Use `npm run generate:assurance-runtime-binding` after changing runtime-capable registry entries. Run `npm run validate:assurance` to enforce registry completeness, JSON Schema validation, generated binding agreement, lifecycle/integrity semantics, deterministic summaries, and operational monitoring controls.

## Browser and HTTP ownership

The assurance registry owns assurance data, not the public browser topology.

The application route registry owns the single human assurance destination at `/assurance` and the canonical reporting HTTP family at `/api/reporting`. `/assurance` is rendered by the application presentation layer as four focused checks over canonical assurance/reporting data; internal registry families do not receive browser routes merely because they exist.

Disclosure projection, filtering, pagination, exact record lookup, response envelopes, CORS, ETags, and cache headers belong to the shared reporting service and `/api/reporting` handlers. Published advisories remain presented through the separate `/security` support boundary.

Canonical risks, incidents, exercises, concerns, governance records, suppliers, objectives, framework records, and other management-system inventories remain governed structured data/reporting collections without being ordinary public HTML destinations. Stable machine record identity and relationship semantics are independent of the human presentation.

Retired assurance child paths use the ordinary 404 response with no aliases or redirects. The executable removed-route fixture remains authoritative for the exact retired browser path set.
