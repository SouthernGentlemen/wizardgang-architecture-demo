## 1. Purpose

This assessment evaluates the reasonably foreseeable positive and negative impacts of the current WizardGang Architecture Demo MCP capability on users, operators, evaluators, and other relevant interested parties.

It is intentionally separate from the AI risk register.

The AI risk register evaluates uncertain events, threats, causes, likelihood, impact, treatment, and residual risk. This assessment instead examines how the AI-facing capability may affect people and interested parties during intended use and foreseeable misuse, including effects that are not purely cybersecurity concerns.

This record supports engineering alignment with ISO/IEC 42001. It does not represent certification, complete AI safety, independent assurance, or an assessment of any third-party general-purpose AI model.

## 2. System Being Assessed

The assessed capability is the public MCP interface implemented by the WizardGang Architecture Demo.

The current server:

- exposes a streamable HTTP MCP endpoint at `/mcp/server`;
- exposes a read-only `ping` tool;
- exposes a read-only `list_demo_records` tool;
- authorizes the caller against the application's `demo:read` permission boundary;
- validates the requested record namespace;
- limits record retrieval to 100 rows per call;
- returns structured output and text representations;
- applies server-side authorization and validation rather than relying on the calling model to enforce policy;
- rejects cross-origin browser requests when an explicit non-matching `Origin` header is supplied;
- records bounded client/tool-call evidence in application logs;
- identifies exposed tools as read-only, non-destructive, and idempotent;
- supports known MCP protocol versions through the checked-in server implementation;
- and does not currently expose MCP tools that write application data, administer the demo, deploy code, change configuration, or perform destructive operations.

The current AI boundary evaluation also exercises:

- an approved read-tool path;
- an unsupported method path;
- and an invalid namespace path.

Those tests provide useful evidence of the present boundary but are not considered a complete safety or impact evaluation.

## 3. What WizardGang Controls

WizardGang controls the parts of the capability implemented within the demo, including:

- which MCP tools exist;
- tool descriptions and schemas;
- application authorization;
- namespace and input validation;
- database queries performed by the tools;
- fields returned by those queries;
- result limits;
- logging and evidence generated by the server;
- failure behavior within the application;
- source control and release of the MCP implementation;
- public documentation and assurance claims;
- and whether future tools receive broader permissions.

WizardGang does **not** control the reasoning, prompting, memory, downstream actions, user interface, or output interpretation of every third-party model or agent that may call the public MCP interface.

That distinction is material to this assessment.

## 4. Intended Use

The current intended use is:

> Allow an AI-capable client or other MCP-compatible tool to inspect bounded public architecture-demo records and verify MCP connectivity through a controlled, read-only application interface.

Expected uses include:

- inspecting public demonstration records;
- validating MCP client interoperability;
- demonstrating how AI-facing tools can share ordinary application authorization boundaries;
- demonstrating read-only, bounded, structured tool behavior;
- testing fail-closed handling of invalid or unsupported requests;
- and allowing technical reviewers to inspect the architecture through an agent-capable interface.

The current MCP capability is **not** intended to:

- make high-impact decisions about people;
- determine eligibility, employment, credit, healthcare, legal status, or similar outcomes;
- autonomously administer the WizardGang system;
- modify source code or production configuration;
- deploy releases;
- delete or mutate application data;
- access private or privileged records through the public tool boundary;
- serve as an authoritative general knowledge source;
- or provide unrestricted authority to an external agent.

## 5. Intended Users and Affected Parties

### 5.1 Direct users

Direct users include:

- developers testing MCP clients;
- technical evaluators and portfolio reviewers;
- AI/MCP users invoking the public tools;
- WizardGang operators validating the capability;
- and automated agents acting on behalf of a user through an MCP-compatible client.

### 5.2 Indirectly affected parties

Indirectly affected parties may include:

- public visitors whose expectations are shaped by the demo's assurance claims;
- people who receive a summary, explanation, or recommendation generated by an external AI using returned demo data;
- maintainers who rely on evaluation and logging evidence;
- security researchers reviewing the public boundary;
- and future users who may be affected if the capability expands beyond its current read-only scope.

### 5.3 Current impact sensitivity

The current capability has relatively limited direct human-impact sensitivity because it exposes bounded public demonstration data and does not make or execute consequential decisions about individuals.

That does not make the impact zero. Misinterpretation, misleading downstream use, unnecessary data exposure, capability drift, or a future increase in authority could materially change the impact profile.

## 6. Data and Inputs

### 6.1 Inputs received from callers

Current tool inputs are limited.

`ping` accepts no application arguments.

`list_demo_records` accepts a `namespace` string constrained by a server-side regular expression and defaulted to `public`.

The MCP transport also receives protocol and client metadata as part of ordinary requests. Client-name, client-version, and protocol-version evidence is normalized and bounded before logging.

### 6.2 Data accessed by the tool

`list_demo_records` reads from the `demo_records` table and returns:

- numeric record ID;
- namespace;
- record key;
- and `valueJson`.

The current intended data boundary is public demonstration data.

### 6.3 Data-quality considerations

Returned records may be:

- synthetic;
- demonstration-oriented;
- incomplete relative to a real production system;
- stale if not maintained;
- or context-limited.

Therefore, availability through MCP must not be interpreted as a guarantee that every returned record is current, complete, authoritative, or suitable for downstream decision-making.

### 6.4 Sensitive-data expectation

Sensitive credentials, authorization material, private account metadata, and other non-public information are not intended to be exposed through the public MCP tools.

A future schema or data-flow change that could expose a new data category requires reassessment before the current impact conclusion can be relied upon.

## 7. Outputs and Actions

The current MCP server returns information; it does not currently perform privileged or destructive application actions.

### 7.1 `ping`

The `ping` tool returns basic server, transport, and timestamp information used to validate connectivity.

### 7.2 `list_demo_records`

The record-list tool returns bounded structured records from the selected valid namespace.

### 7.3 Current action boundary

The current server does not expose MCP tools for:

- creating records;
- editing records;
- deleting records;
- changing user permissions;
- changing admin state;
- changing crawler policy;
- dispatching releases;
- merging pull requests;
- deploying code;
- changing Cloudflare resources;
- or otherwise performing privileged administration.

This read-only boundary is the strongest current impact-limiting characteristic of the capability.

## 8. Human Oversight

Human oversight exists primarily through control of the application and its deployment rather than per-tool-call approval.

WizardGang operators retain human authority over:

- source changes;
- tool definitions;
- permissions;
- schemas and data exposure;
- production configuration;
- releases and deployment;
- privileged administration;
- risk acceptance;
- policy approval;
- and future expansion of the MCP capability.

A human does not manually approve each public read request, because the current read-only capability is intentionally designed for automated invocation inside a predefined authorization boundary.

This oversight model is appropriate only while the capability remains low-authority and read-only.

Any future MCP capability that writes, deletes, administers, deploys, changes permissions, controls external systems, or otherwise creates material consequences must define a new human-oversight model before release.

## 9. Foreseeable Misuse and Misinterpretation

Reasonably foreseeable misuse or misinterpretation includes:

1. **Treating returned demo records as authoritative real-world facts.**
2. **Treating synthetic or stale data as current production information.**
3. **Treating text contained in returned records as trusted instructions rather than untrusted data.**
4. **Attempting to request unsupported, privileged, destructive, or undocumented tools.**
5. **Attempting to escape the intended namespace through malformed input.**
6. **Attempting to use the MCP interface as a path around ordinary application authorization.**
7. **Using external agent behavior to create actions outside WizardGang's system based on MCP output.**
8. **Interpreting successful boundary tests as proof of complete AI safety or ISO certification.**
9. **Assuming client identity evidence is cryptographic proof of the calling model or agent.**
10. **Assuming every future MCP tool will have the same low-impact profile as the current read-only tools.**

The application can directly prevent some of these behaviors, such as invalid namespace access or unsupported server-side actions. It cannot fully control how an external model interprets public text or what a separate downstream system does with returned information.

## 10. Positive Impact Assessment

### IMPACT-POS-001 — Safer demonstration of AI/tool integration

**Affected parties:** Developers, evaluators, AI/MCP users.  
**Potential benefit:** Demonstrates that an AI-facing interface can reuse ordinary server-side authorization and validation rather than receiving special or unrestricted privileges.  
**Current evidence:** `demo:read` authorization, validated namespace, read-only tool annotations, bounded D1 query.  
**Assessment:** Positive and material to the purpose of the demo.

### IMPACT-POS-002 — Increased technical inspectability

**Affected parties:** Reviewers, maintainers, security researchers.  
**Potential benefit:** Machine-readable public records and explicit tool schemas can make system behavior easier to inspect, reproduce, and test.  
**Current evidence:** Public source, structured MCP outputs, explicit tool definitions, evaluation endpoint.  
**Assessment:** Positive, provided public data remains intentionally public and accurately described.

### IMPACT-POS-003 — Demonstration of bounded automation

**Affected parties:** Developers, AI-system designers, evaluators.  
**Potential benefit:** Shows a concrete architecture in which automation is useful without automatically receiving write or administrative authority.  
**Current evidence:** Current tool inventory is read-only; application administration remains separate.  
**Assessment:** Positive and directly aligned with the AI policy.

### IMPACT-POS-004 — Improved traceability of AI-facing behavior

**Affected parties:** Operators, reviewers, future auditors.  
**Potential benefit:** Tool calls and boundary evaluations produce structured evidence useful for troubleshooting, regression detection, and review.  
**Current evidence:** bounded application logs and evaluation audit events.  
**Assessment:** Positive, subject to continued control of logged data and retention.

### IMPACT-POS-005 — Lower barrier to interoperability testing

**Affected parties:** Developers and MCP client users.  
**Potential benefit:** A public, documented endpoint provides a practical interoperability target without requiring privileged system access.  
**Assessment:** Positive, provided availability and protocol limitations are communicated accurately.

## 11. Negative and Adverse Impact Assessment

### IMPACT-NEG-001 — External AI may over-trust demonstration data

**Affected parties:** AI/MCP users and downstream recipients of AI-generated summaries.  
**Scenario:** A model or user treats demo records as current, complete, authoritative facts.  
**Potential effect:** Misleading explanation, incorrect technical conclusion, or inappropriate downstream action.  
**Current controls:** Public architecture-demo context; explicit assurance limitations; bounded data source.  
**Residual impact:** **Moderate.** The server can clarify provenance and limitations, but it cannot guarantee how an external model uses returned data.  
**Related risks:** AI-RISK-006, AI-RISK-010, AI-RISK-013.  
**Treatment direction:** Improve freshness/provenance metadata and integrating-client guidance.

### IMPACT-NEG-002 — Returned content may function as indirect instruction to an external model

**Affected parties:** Users of external AI agents and downstream systems.  
**Scenario:** Text inside a public demo record is interpreted by a model as an instruction instead of data.  
**Potential effect:** Misleading behavior, changed model response, unintended downstream requests, or actions outside WizardGang's system.  
**Current controls:** WizardGang's server-side tool authority remains read-only and validated; record content cannot itself create new server permissions.  
**Residual impact:** **Moderate.** Downstream model behavior remains partly outside WizardGang control.  
**Related risk:** AI-RISK-003.  
**Treatment direction:** Explicitly characterize returned record content as untrusted data and add representative indirect-instruction evaluation cases.

### IMPACT-NEG-003 — Public data boundary may expand unintentionally

**Affected parties:** Users whose information could become exposed, operators, reviewers.  
**Scenario:** A schema, migration, new namespace, or tool change causes data not intended for public AI access to become retrievable.  
**Potential effect:** Confidentiality or privacy impact and loss of trust.  
**Current controls:** Current namespace validation, ordinary authorization, public-source security rules, controlled changes.  
**Residual impact:** **Moderate.** Current data is intended to be public, but future data/schema changes could alter the boundary.  
**Related risk:** AI-RISK-004.  
**Treatment direction:** Maintain explicit public-field/namespace allowlists and test sensitive-field exclusion.

### IMPACT-NEG-004 — Capability expansion could reduce meaningful human control

**Affected parties:** WizardGang operator, users, maintainers, downstream systems.  
**Scenario:** Future tools gain write, admin, deployment, permission, or destructive authority without a redesigned oversight model.  
**Potential effect:** Unauthorized or excessive automation, integrity loss, security compromise, or material actions occurring without appropriate human approval.  
**Current controls:** No such tools are currently exposed; source/release/admin decisions remain human-controlled; AI policy requires explicit review.  
**Residual impact for current capability:** **Low to Moderate.** Current direct impact is limited by the read-only boundary.  
**Future impact if authority expands:** Potentially **Major or Severe** depending on capability.  
**Related risks:** AI-RISK-001, AI-RISK-009, AI-RISK-012.  
**Treatment direction:** Treat authority expansion as a mandatory reassessment trigger and require explicit approval before implementation.

### IMPACT-NEG-005 — Narrow evaluation may create false confidence

**Affected parties:** Operators, reviewers, prospective clients or employers, auditors.  
**Scenario:** A passing three-case boundary evaluation is interpreted as comprehensive AI assurance.  
**Potential effect:** Overstated trust, missed regressions, or misleading public assurance claims.  
**Current controls:** Existing policy and governance text explicitly state that narrow automated evaluation is not proof of complete safety or certification.  
**Residual impact:** **Moderate.** The current wording reduces but does not eliminate misunderstanding.  
**Related risks:** AI-RISK-007, AI-RISK-014.  
**Treatment direction:** Expand the evaluation matrix and present scope/limitations adjacent to results.

### IMPACT-NEG-006 — Client identity metadata may be misunderstood

**Affected parties:** Operators, reviewers, incident investigators.  
**Scenario:** Best-effort client-name or user-agent evidence is interpreted as authenticated proof of a specific AI client.  
**Potential effect:** Incorrect attribution during troubleshooting or review.  
**Current controls:** Identity strings are normalized and used as evidence metadata rather than authorization. Authorization is determined separately.  
**Residual impact:** **Low to Moderate.**  
**Treatment direction:** Explicitly document client metadata as self-reported/best-effort evidence, not identity authentication.

### IMPACT-NEG-007 — Protocol or client incompatibility may create confusing failure behavior

**Affected parties:** Developers and MCP users.  
**Scenario:** Protocol evolution or client implementation differences cause failures, partial behavior, or misunderstood capabilities.  
**Potential effect:** Reduced usability, incorrect conclusions about system availability, or accidental reliance on unsupported behavior.  
**Current controls:** Explicit supported protocol versions and structured MCP handler.  
**Residual impact:** **Low to Moderate.**  
**Related risk:** AI-RISK-011.  
**Treatment direction:** Maintain compatibility tests and clear supported-version evidence.

### IMPACT-NEG-008 — Accessibility or usability limitations may affect interpretation

**Affected parties:** Users with disabilities and users relying on agent-mediated presentation.  
**Scenario:** An external AI client presents MCP results in a way that is inaccessible, ambiguous, or strips important limitation/provenance context.  
**Potential effect:** Unequal ability to understand or safely use returned information.  
**Current controls:** WizardGang controls structured server output and the accessible web demo, but not every external client interface.  
**Residual impact:** **Low to Moderate** within WizardGang's current control boundary.  
**Treatment direction:** Keep outputs structured and concise, expose useful provenance/limitation metadata, and avoid claiming control over third-party client accessibility.

### IMPACT-NEG-009 — Logging may be insufficient or excessive

**Affected parties:** Users, operators, investigators.  
**Scenario:** Too little logging prevents reconstruction of material behavior, while too much logging captures unnecessary user or content data.  
**Potential effect:** Weak accountability or unnecessary privacy/confidentiality exposure.  
**Current controls:** Bounded client metadata, tool name, duration, auth mode, namespace, and result count are logged; security rules prohibit credentials and sensitive data in public logs.  
**Residual impact:** **Moderate.**  
**Related risk:** AI-RISK-008.  
**Treatment direction:** Define an AI-event minimum/prohibited-field standard and validate redaction.

### IMPACT-NEG-010 — AI incident or concern handling may be inconsistent

**Affected parties:** Users, operators, reporters, reviewers.  
**Scenario:** Unexpected AI-facing behavior is observed but no consistent classification, containment, investigation, communication, or corrective-action process exists.  
**Potential effect:** Recurrence, weak accountability, or unresolved harmful behavior.  
**Current controls:** General logging, audit evidence, vulnerability reporting, controlled change process.  
**Residual impact:** **Moderate.**  
**Related risk:** AI-RISK-015.  
**Treatment direction:** Establish an AI incident/concern process linked to corrective action and management review.

## 14. Known Limitations

This assessment has the following limitations:

1. It evaluates the current WizardGang-controlled MCP interface, not every external model or agent that may use it.
2. It does not establish the accessibility, privacy, security, or behavior of third-party MCP clients.
3. It does not establish that all possible malformed, adversarial, or protocol-edge requests have been tested.
4. It does not establish that public demo records are always current or complete.
5. It does not establish that future schemas or namespaces will remain safe without review.
6. It does not assess any future write, privileged, destructive, autonomous, or external-system-control tool.
7. It does not convert self-reported client metadata into authenticated identity.
8. It does not prove that downstream models will follow intended-use guidance.
9. It does not replace the AI risk register, incident process, supplier review, Statement of Applicability, or management review.
10. It is an internal engineering/governance assessment, not independent certification or third-party assurance.

## 15. Residual Impact Conclusion

For the **current read-only public MCP capability**, the direct human and organizational impact is assessed as **limited to moderate** because:

- the capability returns public demonstration data rather than making consequential decisions about individuals;
- it does not currently execute write, administrative, deployment, permission, or destructive actions;
- server-side controls enforce authorization and validation independently of model behavior;
- results are bounded;
- and human operators retain control of material system changes.

The most material residual impacts are informational and governance-related:

- external AI over-trust or misinterpretation;
- indirect instruction injection through returned content;
- unintended future data exposure;
- false confidence from narrow evaluation;
- unclear attribution from self-reported client metadata;
- capability drift;
- and inconsistent AI incident handling.

**No blanket residual-impact acceptance is created by this assessment.** Individual risks remain governed by the AI risk register and explicit acceptance rules.

## 16. Current Proposed Operating Decision

Subject to approval of this assessment through the controlled pull request, the current read-only MCP capability may continue operating **within its existing boundary** while the identified moderate-impact treatments are tracked.

This proposed decision depends on the following conditions remaining true:

- no MCP write or privileged tools are exposed;
- the intended data boundary remains public demonstration data;
- ordinary authorization continues to apply;
- namespace/input validation remains server-side;
- returned results remain bounded;
- security logging restrictions remain in force;
- limitations remain publicly represented accurately;
- and material changes trigger reassessment before release.

This operating decision is not approval for broader AI authority.

## 17. Required Treatment Actions

The following actions should be carried into the AIMS treatment and improvement backlog:

1. maintain a controlled inventory of MCP tools and permissions;
2. add explicit public-field and namespace allowlists where practical;
3. add tests for sensitive-field exclusion;
4. add indirect-instruction/prompt-injection content to the evaluation set;
5. expand the AI evaluation matrix beyond the current three cases;
6. add freshness/provenance or demonstration-data context to returned records where useful;
7. document client identity metadata as best-effort/self-reported evidence only;
8. define minimum and prohibited AI log fields;
9. establish AI incident and concern handling;
10. link material MCP changes to AI risk and impact reassessment;
11. require a new assessment before introducing write, privileged, destructive, or external-system-control tools;
12. carry applicable controls and exclusions into the ISO/IEC 42001 Statement of Applicability.

## 18. Mandatory Reassessment Triggers

This assessment must be revisited before or promptly after any material change involving:

- a new MCP tool;
- a write or mutation capability;
- privileged or administrative authority;
- deployment or source-control authority;
- permission changes;
- cross-namespace access;
- a new data category;
- private or user-specific information;
- material schema or persistence changes affecting MCP output;
- new external-system actions;
- new model or provider integration controlled by WizardGang;
- changed intended use;
- autonomous multi-step execution;
- materially changed human oversight;
- material protocol or transport changes;
- a significant AI incident or credible concern;
- an evaluation failure indicating changed impact;
- or a newly identified affected party or requirement.

A new capability must not inherit this assessment merely because it also uses MCP.
