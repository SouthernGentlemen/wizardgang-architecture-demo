## Scope

Publish the forward patch release for the GitHub-hosted Cloudflare managed-challenge failure discovered during the v0.25.1 deployment attempt.

v0.25.1 successfully reproduced the exact annotated tag, published its release-bound assurance snapshot and GitHub Release, validated the tagged source, and passed the production Worker-secret preflight with all 15 required names. Deployment then stopped before migrations because the first request to `/api/operations/health` returned HTTP 403.

DEMO-309 aligns the deployment baseline with the already proven DEMO-299 monitor behavior: when Cloudflare explicitly marks a first 403 as `cf-mitigated: challenge`, the verifier drains that response and retries exactly once with the same identified request. A second unacceptable response still fails closed and reports only bounded public-safe edge metadata.

DEMO-310 changes release metadata only.

## Included changes

- DEMO-309: retry one explicit Cloudflare managed challenge while capturing the pre-deployment identity baseline, keep a 15-second request timeout, fail closed after the bounded retry, add public-safe edge diagnostics, add executable regression coverage, and record the failed v0.25.1 deployment attempt.
- DEMO-310: set v0.25.2 package metadata and publish this patch release record.

The DEMO-310 pull request must have the repository-required `validate` and `change-id` checks green before merge. The controlled-history validator must report 310 sequential controlled changes on the release branch.

Release-path acceptance must retain all existing gates:

- `.github/workflows/deploy.yml` uses `npx wrangler secret list --format json`;
- release/deploy inline Node remains explicit ESM and parseable by the pinned Node 22 toolchain;
- pre-deployment identity capture retries only one HTTP 403 explicitly marked `cf-mitigated: challenge`, then fails closed;
- migrations run only after secret-name verification and identity-baseline capture succeed;
- deployment checks out the exact annotated semantic version tag;
- post-deployment verification checks exact version and commit, Worker health, identity readiness, and configured-provider continuity.

Immediately before pushing the tag, run the production names-only preflight from an authenticated environment:

```bash
npx wrangler secret list --format json > "$TMPDIR/worker-secret-names.json"
node scripts/validate-worker-secrets.mjs --provisioned "$TMPDIR/worker-secret-names.json"
```

A missing required Worker secret stops the release before the tag is pushed.

## Known limitations

- The Worker-secret preflight verifies names, not secret values, entropy, minimum length, provider-side validity, or every external-provider setting. Runtime readiness checks remain responsible for configuration strength where the application can enforce it.
- The DEMO-300 repository protections are provider-enforced, but ISO/IEC 27001 A.8.25 and A.8.32 remain Partial pending an effectiveness review.
- Most ISO/IEC 27001 and ISO/IEC 42001 requirements remain Partial or Gap where an operating record has not yet occurred. No operating record is created, backdated, or simulated by this release.
- Screen-reader and human visual testing for remaining partial WCAG criteria is still pending. Automated accessibility and localization checks are bounded engineering evidence and do not establish WCAG conformance or certification.
- Identity demonstrations remain dependent on the provider configuration present in the production environment.

No ISO/IEC 27001, ISO/IEC 42001, or WCAG certification is claimed.
