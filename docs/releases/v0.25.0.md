# WizardGang Architecture Demo v0.25.0

**Product:** WizardGang Architecture Demo

**Version:** v0.25.0

**Release date:** the annotated tag's date in UTC — `TZ=UTC git for-each-ref --format='%(taggerdate:short-local)' refs/tags/v0.25.0`

**Commit:** the commit this tag names — `git rev-list -n1 v0.25.0`

## Scope

Release the completed Release Operations Hardening sequence after DEMO-294 through DEMO-305 are merged into `main` and DEMO-306 is merged as the release change.

This release hardens the production release path around Worker-secret prerequisites, identity readiness, deployment evidence, monitoring, repository protection, release-note/tag identity, rollback policy, and pinned build tooling. It also closes the D1 reflow and repeated-link-name defects found during v0.24.0 verification and makes the release-operations acceptance contract executable.

No runtime feature is introduced by DEMO-306 itself. DEMO-306 changes release metadata, release documentation, and planning governance only.

## Validation

Before the annotated release tag is created, the release candidate is required to pass:

```text
npm ci
npm run check
npm run validate:migrations
npm run security:dependencies
npm run build
git diff --check
npm run validate:ci
```

The final DEMO-306 pull request must have the repository-required `validate` and `change-id` checks green before merge. The controlled-history validator must report 306 sequential controlled changes on the release branch.

Release preparation also verifies that `.github/workflows/deploy.yml` uses the locked Wrangler 4.130.0 machine-readable command:

```text
npx wrangler secret list --format json
```

Immediately before the tag is pushed, run the production names-only preflight from an authenticated environment:

```bash
npx wrangler secret list --format json > "$TMPDIR/worker-secret-names.json"
node scripts/validate-worker-secrets.mjs --provisioned "$TMPDIR/worker-secret-names.json"
```

A missing required Worker secret stops the release before the tag is pushed.

## Deployment

Target: `demo.wizardgang.ai`.

After DEMO-306 is merged, create `v0.25.0` only as an annotated tag on that merge commit, with message `WizardGang Architecture Demo v0.25.0`. Pushing the tag triggers the Release workflow and production deployment, so the tag is created and pushed only after explicit operator approval.

This is the first production deployment whose release path runs the DEMO-297 Worker-secret preflight and the DEMO-296 identity-readiness/identity-provider continuity checks. The deploy workflow checks required Worker secret names before migrations, captures the live identity baseline, applies pending D1 migrations, deploys the exact tagged source, then verifies version, commit, Worker health, identity readiness, and continuity of every provider that was configured before deployment.

No change in DEMO-294 through DEMO-306 adds a Worker secret. DEMO-297 adds inventory and verification only, and DEMO-298 removes the orphaned `DEMO_API_TOKEN`. Therefore v0.25.0 has no newly introduced Worker-secret provisioning prerequisite. Production must still contain every secret marked required in `config/worker-secrets.json` before the tag is pushed.

If deployment fails, do not move or delete the published tag. Report the failing step and correct forward under a new controlled change/version unless the documented rollback process is explicitly chosen.

After deployment and post-deployment verification succeed, record the deployment as DEMO-307 (`OPS`) in `docs/history/DEPLOYMENTS.md`, as required by `docs/RELEASE-MANAGEMENT.md`.

## Known limitations

- The Worker-secret preflight verifies names, not secret values, entropy, minimum length, provider-side validity, or every external-provider setting. Runtime readiness checks remain responsible for configuration strength where the application can enforce it.
- The DEMO-300 repository protections are configured and provider-enforced, but ISO/IEC 27001 A.8.25 and A.8.32 remain Partial pending an effectiveness review; this release does not convert governance configuration into an operating record.
- Most ISO/IEC 27001 and ISO/IEC 42001 requirements remain Partial or Gap where an operating record has not yet occurred. No operating record is created, backdated, or simulated by this release.
- Screen-reader and human visual testing for the remaining partial WCAG criteria is still pending. Automated accessibility and localization checks are bounded engineering evidence and do not establish WCAG conformance or certification.
- The `claims` collection remains available through `/api/reporting` without a page consumer.
- Identity demonstrations remain dependent on the provider configuration present in the production environment.
- `/admin` remains private and non-indexable, while `/offline` remains a public but non-indexable recovery surface outside normal navigation.
- Operational machine APIs remain available where declared even though the retired human `/operations` route remains an ordinary 404.

No ISO/IEC 27001, ISO/IEC 42001, or WCAG certification is claimed.

## Rollback target

v0.24.0

v0.24.0 is data-compatible with this release and remains the immutable rollback reference. Rolling back across DEMO-296 would restore the pre-hardening identity failure behavior instead of the disclosure-safe fail-closed `503` contract and public-safe identity readiness field. Rolling back across DEMO-298 would restore the prior unreachable namespace fallback and stale operator-credential documentation, but must not re-provision `DEMO_API_TOKEN`, because current production has no supported authenticator that consumes it.

Because v0.24.0 predates security changes included in v0.25.0, a production rollback deployment record must state those reinstated behaviors and record the owner's explicit acceptance, as required by `docs/RELEASE-MANAGEMENT.md`. Prefer a forward correction when production can still serve safely.
