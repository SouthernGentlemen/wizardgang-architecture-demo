# WizardGang Architecture Demo v0.25.1

**Product:** WizardGang Architecture Demo

**Version:** v0.25.1

**Release date:** the annotated tag's date in UTC — `TZ=UTC git for-each-ref --format='%(taggerdate:short-local)' refs/tags/v0.25.1`

## Scope

Publish the forward patch release for the release/deployment defect found when v0.25.0 attempted to deploy.

The v0.25.0 Release workflow reproduced and published the exact tagged source and passed the Worker-secret names preflight, but deployment stopped before migrations or Worker deployment because the pre-deployment identity-baseline inline Node script mixed CommonJS `require()` with top-level `await` under Node 22.23.2.

DEMO-307 corrects both release/deploy inline Node blocks to explicit ESM and adds an executable Node 22 regression test. DEMO-308 changes release metadata only so that the correction can move forward under a new immutable patch tag instead of moving the published v0.25.0 tag.

## Included changes

- DEMO-307: repair the pre- and post-deployment identity verification inline Node scripts by running them as explicit ESM, add a regression test that syntax-checks every release/deploy inline Node block under the pinned Node 22 toolchain, and accurately record the failed v0.25.0 deployment attempt.
- DEMO-308: set v0.25.1 package metadata and publish this patch release record.

## Validation

Before the annotated release tag is created, the release candidate is required to pass:

```text
npm ci
npm run check
npm run validate:migrations
npm run security:dependencies
npm run build
git diff --check
npm run validate:ci
```

The DEMO-308 pull request must have the repository-required `validate` and `change-id` checks green before merge. The controlled-history validator must report 308 sequential controlled changes on the release branch.

The release candidate must retain the DEMO-305/307 release-path acceptance conditions:

- `.github/workflows/deploy.yml` uses `npx wrangler secret list --format json`;
- every release/deploy inline Node heredoc is explicitly ESM and passes Node syntax validation under the pinned Node 22 toolchain;
- production migrations run only after the Worker-secret names preflight and identity baseline succeed;
- deployment verifies exact tag version and commit, Worker health, identity readiness, and configured-provider continuity.

Immediately before the tag is pushed, run the production names-only preflight from an authenticated environment:

```bash
npx wrangler secret list --format json > "$TMPDIR/worker-secret-names.json"
node scripts/validate-worker-secrets.mjs --provisioned "$TMPDIR/worker-secret-names.json"
```

A missing required Worker secret stops the release before the tag is pushed.

## Deployment

Target: `demo.wizardgang.ai`.

After DEMO-308 is merged and the required checks remain green, create `v0.25.1` only as an annotated tag on the DEMO-308 merge commit, with message `WizardGang Architecture Demo v0.25.1`. Pushing the tag triggers the Release workflow and production deployment.

The workflow must reproduce the exact tagged source, publish this tag-bound release record and assurance registry snapshot, pass the production Worker-secret names preflight, capture the live identity baseline, apply pending production D1 migrations, deploy the exact tagged Worker source, and verify the public version, commit, Worker health, identity readiness, and configured-provider continuity.

The failed v0.25.0 attempt did not apply migrations or deploy Worker source, so production remained on v0.24.0. v0.25.0 remains an immutable published tag and is not moved, deleted, or reused.

After v0.25.1 deployment and post-deployment verification succeed, record the deployment as a separate controlled `OPS` change in `docs/history/DEPLOYMENTS.md`.

## Known limitations

- The Worker-secret preflight verifies names, not secret values, entropy, minimum length, provider-side validity, or every external-provider setting. Runtime readiness checks remain responsible for configuration strength where the application can enforce it.
- The DEMO-300 repository protections are provider-enforced, but ISO/IEC 27001 A.8.25 and A.8.32 remain Partial pending an effectiveness review.
- Most ISO/IEC 27001 and ISO/IEC 42001 requirements remain Partial or Gap where an operating record has not yet occurred. No operating record is created, backdated, or simulated by this release.
- Screen-reader and human visual testing for remaining partial WCAG criteria is still pending. Automated accessibility and localization checks are bounded engineering evidence and do not establish WCAG conformance or certification.
- Identity demonstrations remain dependent on the provider configuration present in the production environment.

No ISO/IEC 27001, ISO/IEC 42001, or WCAG certification is claimed.
